# Q2.4 慢查询诊断

1. 城市条件的前置通配符让 B-tree 无法定位起始区间。原写法还要为每个候选城市计算 `LOWER`。当前库的重音、大小写不敏感排序规则已能将 São 和 Sao 同等处理。改写保留了子串条件，包括 São Paulo 之外的城市。
2. 原执行计划先选 96,211 个已送达订单，再对客户主键做同样多次随机查找。实测符合城市条件的客户只有 21,092 位。该数据上先过滤客户，再使用 `orders(customer_id, order_status, order_purchase_timestamp)` 查订单，能减少回表和日期比较。若时间窗变得很窄，应重新比较以订单为驱动的计划。
3. 商品明细和评价都是订单的一对多关系。一个订单有三项商品、两条评价时，连接后产生六行。每项商品价加两遍，每条评分也被商品数加权。`COUNT(DISTINCT)` 只能修正订单数，去重和分组还要额外维护状态。
4. 第一版使用多个 CTE 预聚合，修复了重复计价。实际计划对商品、评价各扫描一遍大表并重复过滤订单，随后物化临时表。最终方案只为符合条件的订单读商品及其最新评价，减少了无关读。

## 改写和索引

[q2_4_optimized.sql](q2_4_optimized.sql) 中先按城市筛客户，再查满足日期及状态的订单。商品按订单主键前缀聚合。评价按答复时间、创建时间、评价 ID、评分降序取一条。索引 `(order_id, review_answer_timestamp, review_creation_date, review_id, review_score)` 可反向扫描并覆盖评分。原题金额口径是商品价，保持该定义。若指标为含运费 GMV，需在订单内先加上运费。实收、退款、佣金须从独立流水计算。

固定的高频地理过滤可以用标准城市维表，把筛选转换为城市 ID 集合后对客户城市键建索引。确需任意子串时，分词索引对边界的含义与 LIKE 有差异。应先用检索结果圈候选，再用原条件复核，或在明确有高频固定条件时维护可索引标志。

## MySQL 8.4 实测

运行 `python -m q2_sql_analysis.run_sql --benchmark` 可对两条查询预热，交错运行各五次，并查看 `EXPLAIN ANALYZE`。使用原始 Olist 快照。

| 方案 | 实际聚合粒度 | 分组 | 商品价合计（BRL） |
| --- | --- | ---: | ---: |
| 原题 | 23,568 条连接行 | 22 | 2,547,698.71 |
| 改写 | 20,367 笔订单 | 22 | 2,535,313.89 |

原题多计 **12,384.82 BRL**。改写的独立订单数与原查询逐州一致。停止模型请求后的交错对测中位数由 328.8 ms 降至 188.5 ms，约快 43%。计划中的客户探测次数从 96,211 次转为扫描城市后约 21,092 次索引查订单。性能变化基于这份快照，百倍规模需另做压测。

## 其它 SQL 口径

- Q2.1 找到两个已有葡语分类缺译名。便携厨房及食材处理类别有 10 个商品，`pc_gamer` 有 3 个。空分类应进入分类补全流程。
- Q2.2 每月先聚合商品和运费，再按订单数算取消率。送达日期缺失或早于下单时不进入送达用时均值。2017-11 的 7,544 笔中，7,289 笔已送达，37 笔取消，已送达 GMV 为 1,153,364.20 BRL。
- Q2.3 GMV 只取已送达订单中属于该卖家的明细。订单数、去重客户及取消率以 2017 年有卖家明细的订单为基础。全快照 625 笔取消中 461 笔有商品明细，其余无法可靠归给卖家。评价取每单最新一次，客户用跨订单稳定的 `customer_unique_id`，送达晚于承诺日历日才计迟到。州内排序在全体卖家上先算，再截全站前二十。
