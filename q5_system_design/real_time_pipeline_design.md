# Q5.1 Olist 卖家实时数据管道

## 事件流

```text
下单 / 更新状态 / 买家评价 / 物流回执
          │ 同事务写业务记录和 outbox
          ▼
MySQL 8 主库 → binlog CDC → Kafka 按订单或运单分区
                             ├─ 状态消费者 → 卖家实时视图 → API / SSE
                             ├─ 评价分流 → 情感及抽取队列 → 结构化评价表
                             ├─ 物流事件 → 持久定时检查 → 通知 outbox → 卖家
                             └─ 指标增量 → MySQL 分析实例（日汇总） → Redis → 曲线
                                  └─ 对象存储（Parquet 历史事件，用于重放和对账）
```

## 数据与延迟预算

MySQL 主库保存订单、支付、卖家明细、运单、评价正文及 outbox，确保业务写入和事件同成败。CDC 用 GTID 保存位点。Kafka 保存有限时间的版本事件，按订单或运单有序交付，可重放。多卖家订单通过明细映射到各卖家。订单视图按卖家和订单主键 upsert，只接受更高版本，提交至入队、消费和推送分别给 5、10、10 秒。监控从业务提交到后台读到新版本的 P99，目标 30 秒。

评价另设优先队列，触发时间从提交算到分析 worker 开始。预留 15 秒给 CDC 和分流，队列及冷启动控制在 45 秒内。空文及模板文本在本地给情感结果。有明确证据的走规则，有歧义的进 LLM，卖家先看到分析状态。物流按运单保留承诺版本与时区，承诺日过后由持久定时器重读当前状态。未签收且版本仍有效才写告警。以卖家、运单、承诺版本和告警类型组成幂等键，避免延期调整或重放产生重复通知。

分析实例按卖家和本地业务日存订单数、送达额和取消数，状态变化时对旧、新口径做差量。半年曲线读约 184 行，主键为卖家与日期，Redis 缓存常用范围。今日增量从物化视图补齐，接口返回水位，目标 P95 50 毫秒。Parquet 归档包含事件键和版本，供重算和纠偏，避免曲线查询触碰历史明细或生产写库。

## 容量与 LLM 开销

10 万订单每天平均约 1.16 单每秒。若一单产生 8 个事件、峰值为均值 10 倍，约 93 事件每秒。初期用普通分区消费者和 MySQL 物化。100 万单时同口径约 926 事件每秒。按实测积压增加 Kafka 分区和消费者，拆开实时写入与历史重算资源。按卖家哈希分散日汇总写入，热点卖家分桶后归并。

以评价率 60%、每条 250 输入及 120 输出 token、gpt-6-luna 标准价每百万输入 $0.10 和输出 $0.50 为容量假设。每条约 $0.000085。100 万单每天约 2.19 亿评价每年，全量推理约 $18,615，当前规模约 $1,862。评价率 100% 时上界约 $31,025。若只升级 15% 的复杂评价，大规模约 $2,792，另计重试和基础设施。以正文哈希和 prompt 版本缓存，批内短等待合并，按租户设置 token 日预算。价格和延迟需持续复测。 [OpenAI 标准价格](https://developers.openai.com/api/docs/pricing)

## 三项风险与预案

1. **CDC 丢失、乱序或重放。** 保存 GTID 和消费检查点，用事件键去重，以实体版本拒绝回退。每天核对源端与视图的订单数和金额。发现缺口时从最近已知位点补播，用影子表重建汇总后切换。
2. **热点及错报。** 大卖家促销会推高单分区积压。设队列年龄告警，分离实时与回补。告警发送前核对运单当前状态，给晚到回执设短宽限，记录迟发和错发，缺承运商回执时标记待查。
3. **LLM 超时、成本超限或虚构证据。** 限制上下文及并发，超时回到规则并保留待复核状态。每条证据做原文子串校验和隐私筛查。高严重度且低置信样本转人工，禁用模型直接触发处罚或退款。
